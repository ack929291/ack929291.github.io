part1中，Tokenizer把`The capital of France is`转换成了`[785, 6722, 315, 9625, 374]`，随后Embedding根据这些编号取出5个向量。当时这两部分都被当成了一步完成。这篇文章展开Tokenizer，看看一段字符串如何沿着图中的流程，逐步变成模型能够使用的token ID。

## Tokenizer的处理流程

程序处理的是数字，无法直接把字符串送进模型。Tokenizer先对输入字符串进行整理和切分，再把结果转换成一组token ID。Qwen2.5-3B使用的处理顺序如下：

```text
输入字符串
  ↓
NFC规范化             统一规范等价的Unicode表示
  ↓
正则预切分            把字符串分成若干块
  ↓
UTF-8与ByteLevel      展开成字节级基础符号
  ↓
BPE合并               把基础符号合并成最终token
  ↓
查询词表              把token转换成整数编号
  ↓
token ID
```

图中同时使用英文`The capital of France is`和中文`法国的首都是`作为输入。两段文本经过这条流程后，分别得到5个和4个token。下面沿着数据流依次展开每个环节。

## NFC：统一规范等价的Unicode表示

计算机使用Unicode为文字分配编号，这个编号叫作码点。同一个显示结果有时可以由不同的码点序列组成。例如字符`é`既可以直接使用一个码点`U+00E9`，也可以由字母`e`和一个组合重音符号共同表示：

```text
U+0065 U+0301  →  U+00E9
     e +  ́     →     é
```

这两种写法在人眼看来相同，底层序列却不同。假如直接交给后面的切分规则，它们可能得到不同的处理结果。NFC的全称是Unicode Normalization Form C，也就是Unicode规范化形式C。它会把具有规范等价关系的序列整理成统一形式，并尽量使用已经组合好的字符。

图中的两个输入本身已经符合NFC，因此这一阶段的内容没有变化：

```text
"The capital of France is"  →  "The capital of France is"
"法国的首都是"               →  "法国的首都是"
```

NFC处理完成后，后面的环节就可以在一致的Unicode表示上继续工作。

## 正则预切分：把文本分成若干切片

接下来，Tokenizer使用正则表达式匹配文本中的不同内容，并按照匹配结果把连续文本分成若干切片。正则规则决定连续字母、数字、空格、换行和标点分别怎样成组。

Qwen2.5使用的正则表达式由七个分支组成：

```text
(?i:'s|'t|'re|'ve|'m|'ll|'d)    # 's、't、're等英文缩写后缀
[^\r\n\p{L}\p{N}]?\p{L}+      # 连续字母，可带上前面的一个空格或符号
\p{N}                            # 单个数字
 ?[^\s\p{L}\p{N}]+[\r\n]*     # 连续标点或其他符号，可带前置空格和结尾换行
\s*[\r\n]+                      # 换行以及与它相连的空白
\s+(?!\S)                        # 连续空白的前段，或文本末尾的空白
\s+                              # 其余连续空白
```

右侧注释用于说明每个分支大致想匹配的内容，不属于正则表达式本身。其中，`\p{L}`表示Unicode中的字母，英文字母和汉字都属于这一类；`\p{N}`表示数字；`\s`表示空白字符。

对于英文输入，连续字母组成单词，单词前的空格会被放进同一个切片：

```text
"The capital of France is"

→ "The" | " capital" | " of" | " France" | " is"
```

空格和后面的单词放在一起，使Tokenizer能够区分句首的`capital`和前面带空格的` capital`。这种边界信息会一直保留到最终token中。

连续的汉字同样会被`\p{L}+`匹配，因此中文输入在这里形成一个切片：

```text
"法国的首都是"

→ "法国的首都是"
```

预切分还会记录每个切片在原文中的位置。位置采用左闭右开的范围，英文和中文的结果分别是：

```text
"The"       → (0, 3)
" capital"  → (3, 11)
" of"       → (11, 14)
" France"   → (14, 21)
" is"       → (21, 24)

"法国的首都是" → (0, 6)
```

这些偏移量把token和原文位置连接起来。实体识别、文本标注和界面高亮等任务，可以根据它们找到某个token对应的原始字符范围。

## ByteLevel：把所有文字放到256种基础符号上

后面的处理需要建立在一套有限而完整的起始符号上。Unicode包含大量字符，并且还会继续增加；UTF-8可以把任意Unicode字符串编码成一串字节。一个字节只有`0～255`这256种取值，因此256个基础符号就能覆盖单个字节的全部可能。无论一段文本最终得到多少个字节，都可以使用这256种符号逐个表示。

Qwen2.5先把每个切片编码成UTF-8字节，再让ByteLevel把每个字节映射成一个可打印符号。这样，任意合法的Unicode输入都能从同一套256种基础符号开始处理。

英文中的常见ASCII字符各占一个UTF-8字节，所以`The`会直接展开为三个基础符号：

```text
The → T | h | e
```

空格字节经过ByteLevel映射后显示为`Ġ`。整段英文在这一阶段可以写成：

```text
[T|h|e]
| [Ġ|c|a|p|i|t|a|l]
| [Ġ|o|f]
| [Ġ|F|r|a|n|c|e]
| [Ġ|i|s]
```

一个常用汉字通常会编码成三个UTF-8字节。例如`法`的Unicode码点是`U+6CD5`，经过UTF-8编码和ByteLevel映射后的过程是：

```text
法
→ UTF-8字节：E6 B3 95
→ ByteLevel符号：æ ³ ķ
```

完整中文切片一共包含6个汉字，因此从18个ByteLevel基础符号开始：

```text
法 → E6 B3 95 → æ³ķ
国 → E5 9B BD → åĽ½
的 → E7 9A 84 → çļĦ
首 → E9 A6 96 → é¦ĸ
都 → E9 83 BD → éĥ½
是 → E6 98 AF → æĺ¯
```

这些可打印符号只是字节在Tokenizer文件中的保存形式。每个符号仍然对应一个确定的字节，解码时可以沿原路还原出最初的UTF-8文本。

## BPE：让一个token覆盖更完整的内容

BPE的全称是Byte Pair Encoding。经过ByteLevel后，英文通常还是一个字母占一个位置。例如`Paris`会先表示成：

```text
P | a | r | i | s          5个token
```

如果词表中已经包含`Paris`，同样的内容就只占一个位置：

```text
Paris                      1个token
```

进入模型后，这一个token可以直接承载`Paris`这个完整名称，固定长度的上下文窗口也能容纳更多文本。BPE会把有限的词表名额优先交给语料中经常出现的组合，让一个token平均覆盖更完整的内容。

### 先看一组BPE训练

假设训练语料中只有下面三种内容。右侧表示它们各自重复出现的次数：

```text
banana × 5
band   × 2
ana    × 3
```

训练刚开始时，所有内容都由基础符号逐个表示：

```text
banana → b | a | n | a | n | a
band   → b | a | n | d
ana    → a | n | a
```

第一轮统计所有相邻符号。在这组语料中，`a + n`一共出现15次，频率最高：

```text
banana中的a + n出现2次，共 2 × 5 = 10次
band中的a + n出现1次，共   1 × 2 =  2次
ana中的a + n出现1次，共    1 × 3 =  3次
                                                ────
                                                15次
```

于是训练器把`an`加入词表，记录第一条合并规则，并把语料中的`a | n`合并起来。BPE使用从0开始的rank记录规则产生的顺序，因此第一轮规则的rank是0：

```text
rank 0：a + n → an

banana → b | an | an | a
band   → b | an | d
ana    → an | a
```

第二轮的输入就是第一轮合并后的这三组序列。Tokenizer在`b | an | an | a`、`b | an | d`和`an | a`中重新统计相邻组合，此时`an + a`出现8次，于是得到：

```text
rank 1：an + a → ana

banana → b | an | ana
band   → b | an | d
ana    → ana
```

第三轮继续使用第二轮的合并结果进行统计。此时`b + an`出现7次；完成这次合并后，第四轮又从新结果中统计出`ban + ana`出现5次：

```text
rank 2：b + an   → ban
rank 3：ban + ana → banana

banana → banana
band   → ban | d
ana    → ana
```

经过这几轮，`banana`从6个基础符号逐步变成了词表中的一个token。上一轮的输出就是下一轮的输入，每轮新产生的`an`、`ana`和`ban`都会参与下一轮统计，所以BPE能够一层一层形成更长的组合。

### BPE训练在做什么

把上面的案例推广到完整训练语料，每一轮都执行同样的过程：

```text
统计全部训练语料中相邻符号对的频率
  → 找到当前出现次数最多的一种相邻对
  → 把合并结果加入词表
  → 记录一条merge规则和它的rank
  → 合并这种相邻对在语料中的所有不重叠位置
  → 基于更新后的语料表示进入下一轮
```

一轮只选择一种相邻组合，整份语料中的对应位置会一起更新。新组合进入词表后，词表增加一项；本轮的先后序号成为merge rank，越早学到的规则rank越低。

### BPE训练何时停止

BPE训练常用三个停止条件：

1. **达到词表预算。** 训练前先决定最终希望保留多少个token，词表增长到这个数量时停止。
2. **最高频候选低于阈值。** 例如规定相邻组合至少出现2次，剩余候选都只出现1次时停止。
3. **已经没有相邻组合可以继续合并。** 当前语料中没有候选时，训练自然结束。

Qwen2.5最终保存了151387条merge规则，因此它的BPE词表大小是：

```text
256个ByteLevel基础符号
+ 151387次merge产生的新token
= 151643个BPE词表项
```

这里的151643只表示通过ByteLevel和BPE得到的普通词表项。Qwen2.5-3B为模型分配的完整ID空间是151936，剩余的293个ID由特殊token和保留区组成：

```text
151643个BPE词表项
+     22个特殊token
+    271个保留ID
= 151936个ID
```

22个特殊token包括`<|endoftext|>`、`<|im_start|>`和`<|im_end|>`等。它们会作为完整token直接匹配，不参与BPE合并。其余271个ID目前没有普通token映射，Embedding和LM Head仍按照完整的151936个ID保留对应位置。151643描述的是BPE普通词表的大小，151936描述的是包含特殊token和保留ID在内的完整ID空间。

训练结束后，词表、merge规则和每条规则的rank一起冻结，之后的文本都按照这套结果编码。

## BPE推理：按照rank应用已经学到的规则

收到新的Prompt后，前面的NFC、正则预切分和ByteLevel会先把文本转换成一组组基础符号。正则预切分产生的每个切片会分别进入BPE，合并始终在当前切片内部进行。

此时Tokenizer手里已经有训练阶段冻结的merge规则和rank。它查看当前切片中的所有相邻位置，找到记录在merge表里的组合；当多个候选互相重叠时，优先应用rank较低的规则。每次合并都会产生新的相邻关系，因此还要继续检查更新后的序列：

```text
当前切片中的ByteLevel符号
  → 找到当前可用的相邻merge规则
  → 选择rank最低的候选
  → 合并
  → 重新检查相邻关系
  → 当前已经没有可用规则时结束
```

最后一行就是BPE推理的退出条件：当前切片中，已经没有任何相邻组合出现在merge规则表里。此时保留下来的每一项都是最终token。

### 完整看一遍中文的BPE推理

`法国的首都是`经过ByteLevel后，从18个基础符号开始。这里继续使用对应字节的十六进制值来显示：

```text
E6 B3 95 | E5 9B BD | E7 9A 84 | E9 A6 96 | E9 83 BD | E6 98 AF
```

BPE先按照rank逐步合并每个汉字内部的字节。完成前12次合并后，当前序列变成：

```text
法 | 国 | 的 | 首 | 都 | 是
```

此时，当前相邻位置中有三条可用规则：

```text
都 + 是 → 都是    rank =  99876
法 + 国 → 法国    rank = 104072
首 + 都 → 首都    rank = 105858
```

rank最低的是`都 + 是`，因此先得到：

```text
法 | 国 | 的 | 首 | 都是
```

这次合并改变了相邻关系，`首 + 都`已经无法应用。重新检查当前序列后，`法 + 国`仍然是一条可用规则，于是继续合并：

```text
法国 | 的 | 首 | 都是
```

此时三组相邻关系`法国 + 的`、`的 + 首`和`首 + 都是`都没有对应的merge规则，BPE推理结束。最终得到4个token：

```text
法国 | 的 | 首 | 都是
```

英文输入也会从ByteLevel基础符号开始应用相同的过程，最终得到：

```text
The | Ġcapital | Ġof | ĠFrance | Ġis
```

`Ġ`对应原文中的空格，因此解码后的可读形式仍然是`The capital of France is`。

## 查询词表：把token换成整数编号

BPE结束后，每个结果都已经是词表中存在的token。词表保存着从token字符串到整数ID的映射，Tokenizer逐个查询就能得到模型需要的编号。

英文输入的结果是：

```text
The       → 785
Ġcapital  → 6722
Ġof       → 315
ĠFrance   → 9625
Ġis       → 374

token IDs = [785, 6722, 315, 9625, 374]
```

中文输入的结果是：

```text
法国  → 104328
的    → 9370
首    → 59975
都是  → 100132

token IDs = [104328, 9370, 59975, 100132]
```

这些整数是token在固定词表中的编号。相同的Tokenizer会始终把相同的token映射到相同的ID，后面的Embedding可以直接使用ID定位对应的向量。

## 回到整体流程

现在再看part1中被折叠成一步的Tokenizer，它完成的是一条确定的数据加工流程：NFC先统一Unicode表示；正则表达式把文本分成切片；UTF-8和ByteLevel把所有文字落实到256种基础符号；BPE按照语料中学到的merge规则缩短序列；词表最后把token换成稳定的整数ID。

整个过程中，训练阶段产生规则，BPE推理阶段应用规则。正则预切分规定哪些位置允许组合，BPE的rank决定重叠候选的合并顺序，最终得到的token ID则成为Embedding的输入。下一篇继续沿着这条数据流，展开这些整数如何变成`(5, 2048)`的向量。
